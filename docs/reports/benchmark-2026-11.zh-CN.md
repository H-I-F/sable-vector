# ANN 基准实测 — 2026 年 11 月

`benchmarks/bench_vector.py` 的一次实测，把数字摆出来，好让 `nprobe` 照着数据挑，而不是凭感觉。
脚本自带断言：常驻的 `FlatIndex` 是穷举的，recall 按构造就是 1.0，下面每个近似数字都是用
`_recall_at_k` 拿它当 ground truth 算出来的。

## 怎么跑的

```bash
python -m benchmarks.bench_vector \
  --dim 128 --sizes 1000 5000 --queries 30 --ks 10 \
  --nprobes 1 2 4 8 --clusters 16 --stream-reps 2 \
  --metric cosine --seed 42
```

Linux x86-64 容器，Python 3.11，NumPy 2.3.5，`sable` 从工作树源码加载。种子固定，语料和查询集
可复现。`--dim 128` 是刻意比默认的 1536 维小：跑得快些，走的还是同一套核函数。延迟是 30 次查询
的墙钟时间，`qps` 取倒数。

写入：**26,596 vec/s**，用时 0.19 s。

## 老实读这几行

- **这个规模下，精确检索就该是默认。** 1,000 条时，常驻 flat 索引 0.144 ms 给出 recall 1.00，
  比 IVF 在*任何* `nprobe` 下都快——因为 IVF 在给第一个向量打分之前，先得算质心、读倒排桶。
  近似检索不是一个「免费的更快模式」。
- **`nprobe` 买 recall 的价钱是可以预期的。** 5,000 条时，从 1 个分区加到 8 个，recall 从
  0.623 抬到 0.920，p50 从 0.897 ms 涨到 5.860 ms。1,000 条时同一段扫描在 `nprobe=8` 就到了
  1.000——16 个簇里扫 8 个已经是半个语料，曲线自然就平了。
- **流式精确检索卡在磁盘，不卡在计算。** `flat-stream` 的 recall 仍是 1.00，但 1,000 条时
  大约是常驻路径的 8 倍（1.148 ms 对 0.144 ms）。它是给放不进内存的集合准备的，不是默认值。
- **有一处离群值，照实发出来，不抹平。** 5,000 条的常驻 flat 那行 p50 是 3.773 ms，p95 却是
  95.074 ms、mean 29.779 ms。这是 30 次查询里少数几次的预热 / 分配停顿，不是核函数的性质——
  p50 才是有代表性的数，而 p95 正是「别只报一个数」的理由。重跑会动到这些尾部，recall 那一列
  不会变。
- **写入不是瓶颈。** 128 维下 21–27k vec/s 是内存里暂存的速率，不包含每条记录一次持久
  `fsync`；那个边界在哪儿见 ADR-002。

## 这次运行不覆盖什么

生产用的 embedding 宽度（1536 维）、`l2` 与 `dot` 度量、IVF 的训练耗时、并发 reader，以及带真实
`fsync` 的持久写成本。这里的 recall 是拿*同一份*语料上的穷举索引量出来的，所以它不说明上游
embedding 模型的质量。绝对延迟只是一台容器上的快照，把 recall 曲线和比值当作结论更靠谱。
